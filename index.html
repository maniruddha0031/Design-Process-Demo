Section 5 · Effort / Reasoning

Match Effort to the Task

Low / Fast

Small, simple changes

e.g. "Change this button's color to blue."

Medium

Normal development tasks

e.g. "Add a new feature to the dashboard."

High

Complex / multi-file work

e.g. "Debug a complex issue across multiple files."

✓ Advantages of higher effort

  • Better reasoning for complex tasks
  • Better analysis
  • Useful for debugging
  • Useful for architecture decisions

✗ Disadvantages

  • May take longer
  • Can consume more resources/tokens
  • Overkill for simple tasks
Key message: do not always use the highest effort — match effort to task complexity.
Speaker Notes

Effort refers to how much Claude "thinks" before responding. Use Low for small tasks, High for complex debugging or architecture decisions. It's not necessary to always use High.

Section 6 · Project-Wise Folder Structure

One Project = One Project Folder

Projects\ │ ├── Restaurant-Schedule\ │ ├── index.html │ ├── css\ │ │ └── style.css │ ├── js\ │ │ └── app.js │ ├── assets\ │ ├── README.md │ └── .gitignore │ ├── Employee-Dashboard\ │ ├── index.html │ ├── css\ │ ├── js\ │ └── assets\

Why this matters

  • Cleaner context for Claude
  • Easier development
  • Easier Git management
  • Easier GitHub upload
  • Easier deployment
  • Easier collaboration & maintenance
  • Prevents mixing unrelated projects
Speaker Notes

This rule is very important — one project, one folder. Keeping multiple projects in the same folder confuses both Claude's context and the GitHub upload/deployment process.

Section 6 · Project-Wise Folder Structure

Structure Comparison

✗ Bad

One folder ├── Project A files ├── Project B files ├── Project C files └── random files...

✓ Good

Project A\ → its own folder → its own Git repository Project B\ → its own folder → its own Git repository
Speaker Notes

Look at the left side — everything is mixed together, which makes both GitHub upload and deployment confusing. Follow the right side instead: every project gets its own folder and its own repository.

Section 7 · Git-Friendly Project Design

Prefer HTML + CSS + JavaScript for Prototypes

restaurant-dashboard\ │ ├── index.html ├── css\ │ └── style.css ├── js\ │ └── app.js ├── assets\ ├── README.md └── .gitignore

Why this structure works

  • Easy to understand
  • Easy for Claude to modify
  • Easy to review
  • Easy to upload through the GitHub browser UI
  • Easy to deploy using GitHub Pages
  • No unnecessary build setup
  • Easy for team members to maintain
Speaker Notes

For simple UI or prototype projects, plain HTML/CSS/JS is best — no build step required, and it deploys to GitHub Pages without any extra setup.

Section 9 · Test & Validate

Always Ask Claude to Test & Validate Its Own Work

Prompt Ending · Validation Block

"After implementing the changes, test the application yourself. Perform a sanity check of all major functionality, verify that the requested requirements have been implemented, check for obvious UI/UX issues, console errors, broken links, missing assets, incorrect file paths, and other obvious problems. If you find any issue, fix it before considering the task complete. Finally, provide a short summary of what you tested and any issues that remain."

Add this to almost every build/change prompt

Especially for multi-file or agentic changes.

What you get back

A short, reviewable summary of what was tested — instead of silence and hope.

Speaker Notes

This is a "closing instruction" that should be added to the end of every major prompt — ask Claude to test and validate its own work, and request a short summary.

Section 11 · AI Validation vs. Human Review

AI Validation ≠ Human Review

🤖 AI Check

  • Did I implement the requested feature?
  • Does the code run?
  • Are there obvious errors?
  • Are paths correct?
  • Are requirements present?

🧑‍💻 Human Check

  • Is this actually what the user/business wanted?
  • Is the implementation sensible?
  • Is the UX good?
  • Is the architecture appropriate?
  • Are there security concerns?
  • Are there unintended changes?
"Let AI validate the implementation.
Let humans validate the outcome."
Speaker Notes

AI can test its own work — whether the feature was built, whether the code runs. But judgments like "is this right for the business" or "is the UX good" can only be made by a human.

Section 13 · Agentic AI Advantages & Disadvantages

✓ Advantages

  • Multi-file changes
  • Project-wide understanding
  • Strong debugging support

✗ Disadvantages

  • Can make incorrect changes

Section 17 · Public vs. Private

Choosing Repository Visibility

🌐 Public Repository

Anyone can potentially see the source code.

Use for:

  • Portfolio projects
  • Open-source work
  • Public demos
  • Non-confidential prototypes

🔒 Private Repository

Only authorized users can access it.

Use for:

  • Internal projects
  • Company projects
  • Client-related code
  • Confidential / sensitive work
⚠ Never make company, client, or confidential code Public unless explicitly authorized.
Speaker Notes

Don't take this decision casually. If the code relates to the company or a client, keep it Private by default.

Section 20 · GitHub Repository Best Practices

Keep the Repository Clean

Local Project

restaurant-schedule-dashboard │ ├── index.html ├── css\style.css ├── js\app.js ├── assets\ ├── README.md └── .gitignore

GitHub Repository

restaurant-schedule-dashboard │ ├── index.html ├── css/style.css ├── js/app.js ├── assets/ ├── README.md └── .gitignore

Best practices

  • Keep the same clean structure on GitHub as locally
  • One repository per project
  • Always include a README.md
  • Always include a .gitignore
  • Use meaningful commit messages
  • Don't commit build artifacts, logs, or temp files
Speaker Notes

Keep the GitHub repository structure exactly the same as the local project. Always add a README and .gitignore, and keep one repo per project.
